# Seamless local-instance to shared modded server handoff

## Product goal

A user who has already made a modded local XMCL instance work should be able to
select **Deploy to Shared Hosting**. XMCL should collect the relevant instance
state, upload one validated bundle, compile it into immutable server content,
and start the shared service without asking the user to manually recreate the
loader, Java version, libraries, mods, config, or launch command.

Do not treat a local client instance as an automatically trusted server
executable. The server compiler must validate/rebuild server runtime metadata
and generate its own fixed launcher.

## Scope

This is a cross-repository work package:

```text
C:\Users\ci010-4090\Workspace\x-minecraft-launcher
C:\Users\ci010-4090\Workspace\xmcl-web-api
C:\Users\ci010-4090\Workspace\xmcl-shared-minecraft-compiler
```

Create `Voxelum/xmcl-shared-minecraft-compiler` if it does not exist. It owns
the egress-enabled compilation worker. The launcher owns local **client
instance** bundle generation and upload UX. The web API owns durable deployment
state, signed uploads/grants, compiler authentication, and immutable content
selection.

Do not modify unrelated dirty launcher files. Prefer a new package/module plus
narrow service/UI integration. Do not trust local shell scripts, Java paths,
JVM arguments, Docker image names, or arbitrary URLs.

## Existing launcher code is reference only

The launcher has an arbitrary dedicated-server export facility:

```text
packages/instance/server_exporter.ts
xmcl-runtime-api/src/services/InstanceIOService.ts
```

`ServerExporter` is not the shared-hosting feature path. It exports an
arbitrary runnable dedicated server and can generate `server.sh`/`server.bat`;
shared hosting must neither invoke it nor upload its output.

It may be read as narrow prior art for safe file discovery only. The actual
input is a working local **client instance** and its resolved modpack/instance
metadata. The compiler independently produces the dedicated server runtime.

## Local bundle format

Define a versioned archive, e.g. `.xmcl-server-bundle`, containing:

```text
bundle.json
instance/
  mods/
  config/
  defaultconfigs/
  kubejs/
  scripts/
  resourcepacks/
  server.properties
  pack configuration/data files
resolved/
  version.json
  server-side library descriptors
  loader metadata
  mod descriptors
```

`bundle.json` is generated by the launcher and includes:

```json
{
  "schemaVersion": 1,
  "instanceName": "Human-readable local name",
  "minecraftVersion": "1.20.1",
  "loader": { "kind": "forge", "version": "47.2.0" },
  "javaRequirement": {
    "component": "java-runtime-gamma",
    "major": 17
  },
  "runtimeCatalog": { "sha256": "reviewed catalog revision" },
  "files": [
    { "path": "instance/mods/example.jar", "sha256": "...", "sizeBytes": 1 }
  ]
}
```

Rules:

1. The launcher derives version/loader/Java from its resolved local **client**
   instance
   metadata and the reviewed runtime catalog. It does not ask the user to type
   these values.
2. Bundle paths are normalized relative slash paths; no absolute paths,
   `..`, symlinks, devices, FIFOs, Windows junctions, or generated executable
   scripts are permitted.
3. Exclude client-only/private data by default: `logs/`, crash reports,
   screenshots, caches, auth/accounts, launcher metadata, local Java,
   assets, and client resource packs unless explicitly server-relevant.
4. World upload is a separate explicit opt-in migration after the server
   deployment is created. Do not silently upload a local world.
5. Before upload, show a concise review:
   Minecraft version, loader, Java component/major, mod count/size,
   config/data size, excluded client-only files, and whether a world will be
   migrated.
6. Content hashing is streaming and deterministic. Archive size/count/path
   limits must be compatible with web API/compiler limits.

## Server compatibility preflight

The launcher runs a local preflight before upload:

- identify client-only mods when reliable metadata exists;
- flag (not silently remove) mods with unknown server compatibility;
- reject locally known unsupported loader/Java/catalog combinations;
- show warnings for local-only paths/configs;
- permit the user to continue only after acknowledging warnings.

The compiler repeats all security validation. Local preflight is a UX
optimization, not a trust boundary.

## Web API changes

Extend shared modded runtime imports to support:

```text
sourceFormat: "xmcl_server_bundle"
```

Add a dedicated signed upload flow under the existing authenticated shared
service ownership. The server:

1. validates account/service/subscription ownership and idempotency;
2. creates a short-lived exact PUT for one bundle object;
3. records expected hash/size;
4. validates bundle format/hash after completion;
5. freezes compiler input with the launcher-supplied compatibility only after
   revalidating it against the reviewed catalog;
6. sends the compiler an immutable input grant;
7. preserves current selected content/world if validation or compilation fails.

Do not expose compiler/internal callbacks publicly. Bundle download grants are
compiler-specific and cannot be exchanged for node grants.

## Compiler worker

Implement the new compiler as a non-root, ephemeral worker:

1. Download only the exact signed local-client-instance bundle grant.
2. Verify archive, file hashes, schema, compatibility/catalog revision, and
   safe paths.
3. Use locally bundled/reviewed toolchains or approved artifact origins to
   generate a dedicated server runtime. It must not trust/copy `server.sh`.
4. Resolve/verify loader and server dependencies, rebuild a fixed
   `.xmcl/launch.sh`, and write `.xmcl/runtime.json` with the exact reviewed
   catalog component/major/revision.
5. Package server-relevant content to the immutable content key supplied by
   the API and publish only after all hashes validate.
6. Return structured compatibility/warning failures to the user-facing
   deployment record.

The compiler must not receive Docker socket, billing secrets, node credentials,
Object Storage master credentials, or a general bucket credential. It has
approved egress only during artifact acquisition; no customer runtime
container needs egress.

## Launcher UX

Add a clear local instance action:

```text
Instance menu -> Deploy to Shared Hosting
```

Flow:

```text
select existing shared service
-> local preflight/review
-> export bundle
-> signed upload with progress/cancellation/retry
-> compiler/deployment progress
-> optional explicit world migration
-> start service and show assigned address
```

Use the existing XMCL browser/account session and API base configuration; never
persist Object Storage URLs/credentials in the launcher.

## Tests

Launcher:

1. A resolved Forge/Fabric/NeoForge/Quilt instance emits deterministic bundle
   manifest/path hashes and excludes client-only data.
2. Unsafe paths/symlinks/local scripts/private auth data are rejected/excluded.
3. Local preflight presents client-only/unknown-mod warnings.
4. Upload retry/cancel does not expose signed URL/credentials in logs.

API/compiler:

1. Bundle schema/hash/catalog mismatch and cross-account/service grants fail.
2. Compiler rebuilds its launcher and never executes user `server.sh`.
3. Java 8/16/17/21/25 catalog requirements work from local instance metadata.
4. Invalid/failed deployment leaves current content/world selected state intact.
5. Existing `.mrpack`/CurseForge imports remain compatible.

## Acceptance

On a Windows launcher:

```text
working local modded instance
-> Deploy to Shared Hosting
-> review + upload one bundle
-> compiler publishes immutable server content
-> shared service starts
-> user connects with the same modpack
-> explicit world migration (optional)
-> stop/sync and cross-node restore
```

The user should never need to manually choose a Docker image, Java executable,
loader install command, Object Storage setting, or server launch command.
